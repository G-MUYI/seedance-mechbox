# Seedance Skills 审查报告

基于 `shared/references/seedance-prompt-research.md` 的研究结论，对所有 10 个 skills 进行全面审查。

## 执行摘要

**核心发现**：所有 skills 的提示词结构与 Seedance 2.0 最佳实践存在系统性偏差。研究报告明确指出最高权重要素是"参考素材角色分配(22%)、任务描述(18%)、镜头/时间结构(17%)"，但当前 skills 普遍存在提示词过长、否定提示过密、单个 beat 塞太多动作的问题。

**影响评估**：这些偏差会导致：
1. 提示词后半段被前半段冲淡（研究报告明确警告的陷阱）
2. 模型注意力分散，无法聚焦核心意图
3. 生成结果与预期不符，需要多次迭代

**紧急程度**：高。所有 skills 都需要重构。

---

## 一、与研究报告的系统性冲突

### 1.1 提示词长度问题

**研究结论**：
> "社区测试给出的'甜点区'大约在 50–200 词之间"
> "短而结构化的提示往往优于长而抒情的提示"
> "提示太长、修辞太多，后半段把前半段冲淡"

**当前状态**：
- `seedance-mechbox` 的完整版提示词约 **900-1600 个中文字符**（约 450-800 词）
- `seedance-world-cup-mechbox` 核心骨架版仍然超过 **900 字符**
- `seedance-country-mechbox` 类似长度

**问题严重性**：⚠️⚠️⚠️ 严重超标 3-4 倍

**具体表现**：
```
当前结构（seedance-mechbox）：
一、镜头设定（约150字）
二、场景（约80字）
三、人物（约60字）
四、主体（约400字）← 单段过长
五、十二星座规则（约100字）
六、铭牌（约40字）
七、全局动作语义（约200字）← 过度描述
八、时间轴（未完整读取，但从结构看也很长）
```

### 1.2 否定提示过密

**研究结论**：
> "社区对 dedicated negative prompt 存在分歧"
> "保守做法是：先写正向一致性守则，再按平台能力酌情加一两条简短负向约束，别写成一大串 ban list"

**当前状态**：
所有 skills 的 generator.md 中都包含大量否定描述：
- "不生成真实队徽、赞助商、厂牌 logo"
- "不输出照片级真实身体"
- "不能生成完整国旗、官方徽章"
- "避免把国家简化成旗帜、地图轮廓"
- "不要把完整国旗当作贴图"

**问题**：这些否定项分散在提示词各处，累计占比过高。

### 1.3 单个 beat 塞太多动作

**研究结论**：
> "单个 beat 里塞太多动作和镜头"是常见陷阱
> "每个时间点最好只覆盖一个镜头位置、一个动作和一个氛围细节"

**当前状态**（以 seedance-mechbox 为例）：
```
四、主体
初始形态由装甲瓣片与硬边棱面拼合,主分缝沿顶盖、赤道线或棱边贯穿;
顶部嵌入低矮金属圆形启动键,周围有六角或八角锁环。
装甲瓣交界处布六角螺栓阵列,部分螺栓头嵌微光 LED 状态点。
正前端面采用「外框 + 镂空机芯窗」结构:厚壳装甲框内嵌机芯凹窗,
可见层叠齿轮组、X 形连杆、套筒、轴承环、液压柱,窗中心以大轴承
或星形主齿作视觉锚点。其余各面分配狭长状态灯条、散热栅格、卡扣
插槽、铭牌区、阶梯分层、清晰源开口(滑轨、铰链、套筒口)。
```

**问题**：单段描述了 10+ 个视觉元素，模型无法确定优先级。

## 二、提示词结构与权重分配问题

### 2.1 权重倒置

**研究报告的权重排序**：
1. 参考素材角色分配 (22%)
2. 指令/任务描述 (18%)
3. 镜头/时间结构 (17%)
4. 风格/语气 (9%)
5. 上下文/背景 (8%)

**当前 skills 的实际权重分配**（按字符数估算）：
1. 主体细节描述 (35-40%) ← 过高
2. 全局动作语义 (15-20%) ← 过高
3. 镜头设定 (10-15%)
4. 时间轴 (未完整读取，但从结构看约 15-20%)
5. 场景/人物 (10%)

**问题**：把大量篇幅用在"主体细节"和"动作语义"上，而这些在研究报告中权重较低。

### 2.2 缺少参考素材角色分配

**研究结论**：
> "参考素材角色分配"是最高权重要素 (22%)
> "@Image1 作为人物外观，@Image2 作为材质/场景，@Video1 作为镜头运动"

**当前状态**：
只有 `seedance-mechbox` 提到：
```
如果有参考图：@Image1 作为 {车型} 的外观比例与设计语言参考
```

但其他 9 个 skills 都没有明确的参考素材角色分配策略。

**建议**：每个 skill 都应该在模板中预留参考素材位置，并明确其职责。

### 2.3 时间轴结构不清晰

**研究结论**：
> "时间轴 prompting"是很高推荐度技法
> "5 秒用 2–3 个时间点，10 秒用 3–4 个时间点更合适"
> "显式控制节奏、镜头落点、动作顺序"

**当前状态**：
- `seedance-mechbox` 的"八、时间轴"部分未完整读取，但从前文看结构复杂
- `seedance-world-cup-mechbox` 提到"5 个以内时间 beat"
- 但都没有采用研究报告推荐的简洁时间戳格式：`[0s] ... [3s] ... [6s] ...`

**建议格式**（来自研究报告）：
```
[0s] 建立镜头...
[3s] 缓慢 dolly in...
[6s] 特写落点...
全局 style line 置于末尾。
```

## 四、AGENTS.md 的问题

### 4.1 输出规则冲突

**AGENTS.md 第 45-48 行**：
```
Final Seedance prompts must be long enough for direct use: keep all required
sections, timeline beats, mechanical rules, material details, camera rules,
physical continuity, and key constraints. Do not collapse them into a brief
prompt or a bullet summary.
```

**与研究报告的冲突**：
历史审查曾认为更短的结构化提示更符合当时的优化方向。

**问题**：AGENTS.md 强制要求"长提示词"，这与 Seedance 2.0 的最佳实践直接矛盾。

### 4.2 时间处理规则不清晰

**AGENTS.md 第 49-51 行**：
```
When duration instructions conflict, do not write exact seconds in the final
prompt. Use stage-based progress instead, and preserve the completion nodes
from `shared/references/completion-rules.md`.
```

**问题**：
1. 研究报告推荐使用时间戳格式 `[0s] [3s] [6s]`
2. AGENTS.md 却说"不写精确秒数"
3. 这两者需要协调

### 4.3 缺少权重指导

AGENTS.md 没有引用研究报告中的权重分配建议，导致各 skill 自由发挥，结果都偏离了最佳实践。

   - 删除大部分否定约束，只保留 1-2 条关键的
   - 精简重复的"主体"段落，但保留目标识别、时间轴和物理连续性
   - 删除重复的"全局动作语义"描述

   ```diff

   + output contract. Compress only when the platform gives a hard limit.
   ```

3. **添加权重分配指导**到 AGENTS.md
   ```markdown
   ## Prompt Weight Allocation (from research)
   
   Based on seedance-prompt-research.md, allocate prompt content as:
   1. Reference asset job assignment (22%) - if using @Image/@Video/@Audio
   2. Task description: subject, action, scene (18%)
   3. Camera & timeline structure (17%)
   4. Style & lighting (9%)
   5. Context & background (8%)
   6. Constraints (7%)
   7. Parameters (7%)
   
   Avoid over-investing in detailed mechanical descriptions or long ban lists.
   ```

### 5.2 高优先级修复（P1）

6. **简化映射表处理**
   - 映射表保留在 generator.md 中作为查询逻辑
   - 最终提示词只包含选中的那一项，不包含整个表

## 九、风险评估

### 高风险
- **用户习惯**：如果用户已经习惯当前的长提示词格式，突然改短可能引起不适
- **缓解措施**：统一保留完整版本；只有硬字符限制时做结构保留型压缩

### 中风险
- **功能完整性**：压缩提示词可能丢失某些细节控制
- **缓解措施**：通过参考素材和时间轴结构补偿

### 低风险
- **兼容性**：AGENTS.md 的修改可能影响现有工作流
- **缓解措施**：向后兼容，保留旧规则作为 fallback
